# Mica 简历四点：面试怎么讲、怎么引出核心追问

本文按简历四点组织，依据当前 `mica/` 正式代码、SQL 和测试核对。每点先给可直接练习的短讲，再提供被追问后的展开路线。业务案例用于解释功能，不代表已经发生的客户案例或线上事故；日期、个人职责、部署规模和收益数据需要按真实经历补充。

## 先校准简历口径

| 简历表述 | 代码核对结果与建议 |
|---|---|
| `LangGraph` | 正式包及依赖中没有使用。当前编排由应用服务、数据库状态和 Daemon 实现。建议改成 `Python / FastAPI / PostgreSQL / ACP / A2A / 多 Agent`；其他项目或原型的 LangGraph 经历单独讲。 |
| “保证处理顺序” | 限定为同一 Issue、同一 Agent 的执行先后，以及本轮评论按存储时间排序；不要扩展成跨渠道全局严格有序。 |
| “同一任务复用会话” | 更准确是同一 Issue 与 Agent 下，后续新 Task 复用历史执行上下文。Issue 是持续事项，Task 是一次执行。 |
| “代码任务创建独立 Worktree” | 项目支持 `worktree` 和 `in_place` 两种模式。建议写“支持独立 Git Worktree 执行”。 |
| “Leader 基于 Issue 上下文” | 有标题、正文、委派说明和成员结果摘要；CLI Agent 可经 `mica-ctx` 自助读取评论全文，但没有自动 Artifact 依赖传递。 |
| “进度同步展示在 Web 与飞书” | Web 展示执行事件；飞书回传受理、等待补充、完成、失败等关键消息，未逐条同步流式进度。 |

下面的讲稿已经采用这些边界。第一次回答只讲场景、方案和一个关键取舍；面试官追问后再展开数据库字段、协议和异常路径。

## 项目开场：先用 30 秒说明解决什么问题

> Mica 的核心思路是把 AI Agent 当同事用。用户在任务看板或飞书里写一个事项，像派活一样指派给一个 AI 同事或一个小队；Agent 接活执行，人随时补充要求、追问进展，Agent 交回结果后由人审核，验收通过事项才算完成。企业里既有开发者电脑上的 Coding Agent，也有已经部署好的业务 Agent，平台把这两类 Agent 统一成可指派、可追问、可验收的"同事"，自己负责排队执行、合并补充要求和记录结果。我这部分主要围绕输入合并、本地执行、异构接入和小队编排展开。

如果只有一分钟讲整个项目，四点各用一句业务价值即可，不要在开场报完所有类名和协议。涉及“我负责”的范围，按自己的实际贡献调整。

## 一、多渠道任务触发与合并

### 业务场景：用户的要求是逐步说完整的

以“排查订单同步失败”为例。用户先提交任务，接着补充异常日志、时间范围，再补一句“暂时不要修改代码”。如果每条消息都启动一次 Agent，就会重复分析；如果把后来的消息直接塞进正在执行的任务，又难以解释这轮究竟依据哪些要求行动。

这个功能的作用是：**保留每条补充，尽量让同一轮一起处理；已经开始的一轮保持输入边界，后续要求排到下一轮。** 另外，用户回复某个 Agent 的结果时，应继续找对应 Agent，而不是总找事项默认负责人。

### 第一轮讲法：约 45～60 秒

> 这个功能主要解决用户分多次补充需求的问题。比如用户让 Agent 排查订单同步失败，随后连续发来日志、时间范围和处理限制。如果一条消息触发一次执行，就会重复分析，也可能基于不完整要求开始工作。
>
> 我把持续事项和单次执行分开：Issue 保存目标和讨论，Task 表示一次 Agent 执行。入口先做重复事件去重，再根据显式提及、回复关系或默认负责人找到 Agent。同一事项、同一 Agent 还没领取的 Task 可以合并补充；已经领取后，新要求进入一个待执行的后续 Task。
>
> **这里我重点处理了两个时刻：并发消息到达时只能合并出一个待执行任务，Agent 领取时要固定这一轮实际消费的输入。**

最后一句是主埋点。说到这里停下，让面试官选择问“并发怎么保证”或“为什么固定输入”。不要紧接着把所有 SQL 都解释完。

### 被问“大概怎么实现”时的路线

1. **渠道去重**：`IngressService.submit()` 按渠道、租户、外部事件 ID 预留事件，相同 ID 但不同请求内容会报冲突；新事项、首个 Task、来源映射和受理 Outbox 在事务内写入。
2. **找到执行者**：新 Issue 按指派创建任务；评论优先处理 `@agent:ID` / `@squad:ID`，其次追溯父评论关联的 Agent/Task，再回退默认负责人。纯人工讨论分支存在不触发 Agent 的处理。
3. **原子合并**：PostgreSQL 部分唯一索引约束 `(issue_id, agent_id)` 在 `queued` 状态最多一条，`ON CONFLICT … DO UPDATE` 保存被合并评论的 ID。原始 Comment 不被覆盖。
4. **领取与定界**：领取 SQL 排除同一 Issue/Agent 已有 `dispatched/running` 的情况，使用行锁及 `SKIP LOCKED`，在切到 `dispatched` 时写入 `delivered_comment_ids`。
5. **组装输入**：Prompt 只取本轮记录的评论集合，并按 `created_at, id` 排序；领取后才到达的评论进入后续 Task。

### 引导追问与回答要点

| 可以自然说出的埋点 | 希望引出的提问 | 回答的核心 |
|---|---|---|
| “去重和合并分别处理。” | 两者有什么不同？ | 去重处理同一个事件被重发；合并处理多条不同的有效输入。前者避免重复受理，后者减少执行次数，不能丢掉任何一条真实补充。 |
| “唯一性放在数据库里。” | 为什么不能先查有没有 Task？ | 并发请求可能同时查到不存在。部分唯一索引守住不变量，UPSERT 完成冲突更新；Python 进程锁无法覆盖多实例。 |
| “领取是本轮输入的边界。” | 为什么不直接读取所有评论？ | 读取全部评论会把后来的输入混入本轮，也可能带入发给其他 Agent 的评论。保存消费集合能解释本轮依据；它固定的是评论 ID 集合，不是完整 Prompt 的不可变归档。 |
| “执行中只保留一个待执行后续任务。” | 后续任务会不会和前一轮并发？ | 领取条件排除同一 Issue/Agent 的活跃任务。前一轮正常结束后，后续 Task 才能领取。范围是这对 Issue/Agent，不是整个系统串行。 |

一个最容易讲清的例子：A、B 两条补充在领取前到达，进入 T1；领取后到达 C、D，进入 T2。T1 的 Prompt 包含 A、B，T2 等待 T1 结束后处理 C、D。“减少调用”是这种机制的预期效果，目前没有可引用的线上节省百分比。

### 面试时要守住的边界

- 这是按排队状态合并，不是等待固定几秒的防抖窗口；Agent 很快领取时，消息仍可能分成多轮。
- 飞书只有 `parent_id/root_id` 命中已保存的来源消息，才能接回已有 Issue。同群连续发消息不等于自动接续同一事项。2026-10-09 起 bot 的受理与终态消息改为回复用户首条消息（KI-008 方案一），回复 bot 消息因 `root_id` 链命中已能接回原 Issue。**2026-10-10 起该入站路由整体移除（KI-001）**：飞书消息一律走 ChatSession binding 路由，`issue_origin` 只作出站锚点；本条仅保留为 KI-008 阶段的历史边界。
- 飞书已有 Issue 的追加路径目前没有传 `parent_comment_id`，解析出的 `agent=...` / `squad=...` 也没有传给评论路由。因此不能声称飞书与 Web 已具备完全相同的回复路由能力。
- 租约过期恢复还有异常边界，不能把正常领取流程描述为所有故障条件下的 exactly-once 执行保证。

## 二、本地 Agent 隔离执行

### 业务场景：多项代码工作同时发生，而且会反复修改

同一仓库里，用户可能同时让一个 Agent 修复导出异常，另一个 Agent 调整接口。如果都在同一个目录里修改，文件和分支容易互相干扰。第一轮产出后，用户又会追加“补一个大数据量测试”；这时需要延续已有代码和分析过程。

这个功能的作用是：**控制电脑上同时运行多少 Agent，分开不同事项的代码工作空间，并让同一事项的后续执行能接着做。**

### 第一轮讲法：约 45～60 秒

> 本地 Coding Agent 会真实启动进程、读写代码，所以只在服务端建一个任务队列还不够。比如两个事项同时改一个仓库，如果共用工作目录，会互相影响；用户追加要求时，如果每次换目录，又会丢掉前一轮工作。
>
> 我用本地 Daemon 执行任务，先预留 Runtime 的可用名额，再从数据库领取。项目采用 Worktree 模式时，按 Issue 和 Agent 建立独立分支和目录，后续新 Task 查找历史执行，继续使用原来的分支、目录和 Agent 会话。
>
> **这里要分别续接代码状态和对话状态，只有其中一个是不够的；并发容量也要在领取任务之前拿到。**

这段优先引导“为什么两类状态都要续接”。如果岗位偏后端基础设施，可以只保留最后半句，引到调度与租约。

### 被问“大概怎么实现”时的路线

1. `RuntimeSlotPool.acquire()` 先预留名额，无容量就不领取；`finally` 中释放，避免异常后名额泄漏。
2. Daemon 按 Runtime 领取 Task，数据库记录 `claimed_by`、`attempt` 和租约到期时间。
3. 查询同一 `(issue_id, agent_id)` 的历史执行，取 Session、分支与 Worktree 路径。
4. `WorktreeManager.prepare()` 校验源仓库，创建或复用分支与目录；Git 元数据操作有仓库锁。当前源仓库存在未提交修改会拒绝准备。
5. 将执行上下文绑定到 Task，运行 Provider；Codex/Claude 适配器使用对应的会话恢复参数。执行结果再保存 Session，供下一轮查询。
6. 运行中通过心跳续租，取消通过统一回调传给 Provider；本地 CLI 在 POSIX 下尝试向进程组发送终止信号。完成写回校验 worker 和 attempt。

### 引导追问与回答要点

| 埋点 | 预期提问 | 回答的核心 |
|---|---|---|
| “代码状态和对话状态分别续接。” | 为什么复用 Session 还不够？ | Session 延续 Agent 的分析历史，Worktree 保存真实文件修改。只有 Session，代码目录可能不匹配；只有目录，Agent 又可能重复分析并丢掉此前决策背景。 |
| “先拿容量，再领任务。” | 反过来会怎样？ | 任务已被标成领取态并开始计租约，却没有执行资源。先拿 Slot 可以避免本机资源不足造成的无效占用；Slot 本身是进程内计数，并非跨 Daemon 的全局配额。 |
| “任务所有权有租约和代次。” | Daemon 崩溃后怎么办？ | 过期任务可重新排队，重新领取递增 attempt；旧 worker 的终态写回会被所有权检查拒绝。它保护数据库状态，无法撤销已经发生的文件或远程副作用。 |
| “Worktree 按 Issue/Agent 复用。” | 为什么不按每个 Task 新建？ | 用户对同一事项会多次追问，每轮新建会切断代码连续性；Issue/Agent 既区分执行者，也让该执行者能延续工作。 |

### 模型更新（2026-10-08）：一次性副本 + 分支交付，并打通“A 生成 → B 审核”

上面第一轮讲法、实现路线第 3～4 步与追问表中“继续使用原来的分支、目录”“Worktree 按 Issue/Agent 复用”“源仓库存在未提交修改会拒绝准备”的口径，描述的是 2026-10-08 之前的持久副本模型，保留供对照。当前版本对齐 Multica：

- **每轮新建副本，续接的是分支和会话**：Worktree 落在 Daemon 管理的 `<root>/<repo-hash>/<task-id>/`，收尾即回收；跨轮持久的是用户仓库里的 `mica/<issue>/<agent>` 分支（命名不变）和 CLI 会话（Claude 跨目录 resume 已实测）。“为什么不按每个 Task 新建”的新答案：代码连续性由分支保证，目录本来就不必持久；持久副本反而会继承上一轮残留、冻结基线、永久占用分支。
- **脏仓库不再拒绝**：用户未提交修改打成快照注入副本；两轮之间用户改了 Agent 改过的文件会在副本里形成真实冲突，冲突文件写进下一轮 prompt，未解决前拒绝交付。
- **交付契约**：收尾自动提交残留改动、回收副本，结果评论附分支名与 tip commit；分支已合入主干时下一轮重置到最新 HEAD。
- **A 生成 → B 审核**：分支引用是跨 Agent 传递代码产物的通用载体——审核 Agent 在同一仓库的任意副本里执行 `git diff HEAD...<分支>` 即可看到生成 Agent 的本轮改动，无需共享分支或检出。
- **新边界**：依赖不跨轮保留；finalize 提交与状态回写之间有崩溃窗口，由分支续接兜底；旧模型遗留分支一律冻结不续接。下文“面试时要守住的边界”中“失败残留的目录与分支不清理”一条随之作废：失败/取消的现场保留为 `worktree-preserved`，Daemon 启动时由 `sweep()` 统一回收。

面试讲法可在原 45～60 秒版本基础上替换一句：“后续新 Task 查找历史执行，续接同一交付分支和 Agent 会话；Worktree 副本每轮新建、用完回收，分支是唯一持久成果。”

### 面试时要守住的边界

- Worktree 提供代码工作目录隔离，不是容器或操作系统安全沙箱；不同分支最终仍可能发生合并冲突。
- 项目也支持 `in_place` 模式，当前通过进程内目录锁串行化同目录执行；无项目的本地 Agent 使用受管理的空目录。
- 当前 Session 查询未按 Squad 角色隔离，也没有完整的不可恢复 Session 降级机制。不要说“上下文绝不丢失”。
- 心跳自领取后立即运行，Worktree/Session 准备阶段与执行阶段同样处于续租保护下；准备期间失去租约时会在启动 Provider 前放弃并交回过期恢复。但 Worktree 准备本身不可中断、失败残留的目录与分支不清理，已发生的副作用不能撤销，不能声称具备 exactly-once 或完善的故障恢复。

## 三、异构 Agent 接入

### 业务场景：企业已有能力不应该为了接入平台全部重写

本地 Codex 能修改代码，远程 Geometry Agent 能做几何约束校验，Placement Agent 能生成布局方案。它们的位置、接口和返回结果都不同，但用户希望用同一套任务界面查看状态、补充信息、取消和获取结果。

这个功能的作用是：**让平台接入不同执行能力，同时让任务业务保持一致。** 这里的统一是执行契约统一，不要求各个 Agent 暴露完全相同的内部能力。

### 第一轮讲法：约 45～60 秒

> 企业里的 Agent 并不都是一个框架开发的。有些是电脑上的 Coding CLI，有些是已有的远程业务服务。如果每接一个 Agent 都让任务服务兼容一遍它的格式，上层代码会越来越复杂。
>
> 我定义了统一 Provider 接口：上层传入任务、工作目录、历史会话和取消检查，Provider 通过回调上报执行事件，最后返回结果和会话信息。本地分别用 CLI 和 ACP 适配，远程通过 A2A 发现接口、发起调用并跟踪任务；Web 和任务服务消费同一套事件。
>
> **比较关键的是统一任务语义，例如远端要求补充信息不能当成执行失败，返回了 JSON 也不代表结果就能被下游使用。**

这段引到“等待输入状态”和“结果契约”，比仅说“用了适配器模式”更能体现业务理解。

### 被问“大概怎么实现”时的路线

| 层次 | 当前实现 | 对上层的作用 |
|---|---|---|
| Provider 契约 | `run(agent, issue, task, on_event, workdir, resume_session_id, is_cancelled)`；返回 `ProviderRunResult` | Daemon 用统一入口执行，不到处判断具体协议。 |
| CLI | 子进程读 JSONL，分别解析 Codex/Claude 事件，提取文本、工具调用和 Session | 将 CLI 输出映射为 `agent.text`、`agent.tool` 等 TaskEvent。 |
| ACP | stdio JSON-RPC 初始化，创建或加载 Session，提交 Prompt，处理更新、权限请求和取消 | 封装本地 Agent 的协议交互。 |
| A2A | 读取 Agent Card，选择 HTTP+JSON 接口、校验 Skill；发送消息后处理直接结果或轮询远端 Task | 接入远程执行，保留远端上下文和任务标识。 |
| 结果与等待 | `requires_input` 表示需要补充；配置 `output_schema` 时校验 JSON | 防止把等待当失败、把结构不合规的结果当成功。 |

### 引导追问与回答要点

| 埋点 | 预期提问 | 回答的核心 |
|---|---|---|
| “统一语义，不只是统一函数签名。” | 接口相同还不够吗？ | 还要处理完成、失败、等待输入、取消和恢复。如果远端等待用户输入而本地标成功，用户就无法正确续接。 |
| “远程等待输入可以续接。” | 怎么继续原远端任务？ | A2A Session 编码保存 `contextId`、远端 `taskId` 和状态。普通后续请求复用 context；此前处于可继续的等待状态时，再带上原 taskId。本地 Task 进入 `waiting_input`，Issue 进入 `blocked`。 |
| “JSON 返回成功也要校验。” | HTTP 200 为什么不算成功？ | 传输成功不代表字段、类型符合业务约定。配置 Schema 后，缺少必需字段或类型错误会使本次结果失败。Schema 能检查结构，不能证明业务结论正确。 |
| “取消通过统一回调传入。” | 本地和远程怎么分别取消？ | CLI 尝试终止本地进程，ACP 发送会话取消并清理进程，A2A 调用远端 Task cancel。统一取消意图，具体动作仍由协议适配器完成，不能承诺远端副作用会回滚。 |

如果被问“为什么既有 CLI 又有 ACP”，可以答：CLI 适配已有命令行工具，ACP 提供另一种本地协议接入方式；平台以 Provider 扩展，不要求存量工具先迁移。

### 面试时要守住的边界

- 当前 A2A 实现使用 HTTP+JSON 请求与轮询；即使 Agent Card 声明 streaming，也不能据此声称实现了 SSE 流式订阅。
- 统一事件允许不同 Provider 上报各自具备的信息，不代表平台能获取远程 Agent 的所有内部工具调用。
- `output_schema` 是可选配置；不要说所有 Agent 输出都经过业务 Schema 校验。
- ACP 的权限请求有独立策略，默认拒绝；不能把这套策略泛化成所有 CLI 都有统一的人机审批流程。

## 四、Squad 与飞书协作

### 业务场景：一个结果需要多个专业能力配合

以空间方案为说明案例：用户提供房间信息，希望得到符合约束的摆放方案，必要时还要修改本地展示代码。Geometry Agent 校验约束，Placement Agent 生成方案，Coding Agent 修改代码，Leader 决定各阶段找谁、最后如何汇总。

这个功能的作用是：**把用户逐个找 Agent、搬运结果、判断谁已做完的协调工作交给一个可追踪的小队流程。** 有依赖的步骤应分轮委派；不能把“几何校验后生成布局”说成平台已经自动推导了数据依赖 DAG。

### 第一轮讲法：约 45～60 秒

> 单个 Agent 可以完成局部工作，但跨专业任务往往需要用户自己转交结果。比如先做约束校验，再生成布局，最后调整展示代码，用户不应该每一步都重新找一个工具。
>
> 我支持在 Web 里把本地和远程 Agent 按角色、能力组装为 Squad，并指定 Leader。用户从 Web 或飞书把 Issue 指派给小队后，先启动 Leader，让它根据成员清单和协作规则输出结构化委派，平台校验后创建成员 Task；本批成员都交回控制权，再唤醒 Leader 汇总或继续委派。
>
> **这里模型负责决定怎么分工，平台负责保证委派合法、汇总时机正确；成员完成也不代表整个事项已经完成。** Web 可以查看执行过程，飞书接收关键状态和整体结果，最终由用户验收。

主埋点是“模型决策与平台约束的分工”。如果面试官偏并发一致性，补一句“多个成员同时结束时，也不能重复唤醒 Leader”。

### 被问“大概怎么实现”时的路线

1. **组队与入口**：Squad 保存 Leader、协作说明；成员保存角色和能力标签。Issue 的负责人仍为 Squad，首个 Task 指向 Leader。
2. **Leader 输入**：Daemon 注入成员 roster、规则和结果摘要，让 Leader 返回 `delegate/complete` JSON。
3. **验证与派发**：应用服务验证目标属于非 Leader 成员、没有重复成员、委派指令不为空；验证通过后持久化决策和成员 Task。
4. **批次追踪**：成员 Task 的 `delegated_from_task_id` 指向本轮 Leader Task；平台据此判断同批成员是否仍有 `queued/dispatched/running` 任务。
5. **汇总调度**：在 Issue 行锁内检查批次和已有待处理 Leader，条件满足才排入汇总任务。成员处于等待输入时也视为交回控制权，避免无限等成员完成。
6. **人工验收与渠道回传**：Leader 确认整体完成后把 Issue 推进 `in_review`；事件投影生成持久化 Outbox，投递 Worker 异步发送飞书消息，失败退避并限制重试次数。

### 引导追问与回答要点

| 埋点 | 预期提问 | 回答的核心 |
|---|---|---|
| “先运行 Leader，再决定成员。” | 为什么不广播给所有 Agent？ | 每项任务需要的能力不同，广播会产生无效调用且无人负责收口。Leader 看角色、能力和规则做选择；能力标签用于提示，当前没有独立的能力匹配评分引擎。 |
| “模型输出先校验才能变任务。” | Leader 幻觉出一个成员怎么办？ | 校验结构、成员白名单、重复指派和非空说明，不合法就失败并阻止派发。它保证编排结构合法，不保证拆分方案一定合理。 |
| “同批成员交回控制权才汇总。” | 多个成员同时完成怎么避免重复？ | 用委派来源标识批次，事务中锁住 Issue，检查同批活跃成员和已有待处理 Leader；其他完成回调进入临界区后能看到已有调度结果。 |
| “等待输入也交回 Leader。” | 为什么不一直等 Worker 成功？ | Worker 已释放执行资源，正在等外部输入；一直当成活跃会卡住批次。让 Leader看到等待或失败状态，再协调补充或后续委派；没有固定的自动补救策略。 |
| “任务结果与飞书发送分开。” | 飞书接口失败会不会丢结果？ | 结果事件先持久化，再投影到 Outbox；投递使用租约、退避重试和最大次数。Outbox 按来源事件去重，发送带稳定消息 UUID，但不能宣称跨系统 exactly-once。 |

### 如果被追问“多 Agent 共享上下文怎么做”

这是最需要如实说明的一题，可以直接这样回答：

> 当前共享主要靠 Issue 标题正文、Leader 的委派说明，以及回传的成员结果摘要。Worker 不会自动获得所有历史评论或其他成员的完整结果，但 CLI Worker 和 Leader 现在可以通过任务级只读通道 `mica-ctx` 自行扫描和展开完整评论——通道是可达的，是否读取仍取决于模型行为，且 ACP/A2A 成员尚未接入。因此我会把它定义为已经打通委派、汇总和按需读取的闭环，而不是完整的共享记忆。下一步要给 Task 显式记录依赖的评论、结果和 Artifact 引用，再区分 Leader、Worker 的 Session 作用域，避免只靠提示词搬运上下文。

最后一句属于后续设计方向，必须明确说“下一步”。不要用“自动共享上下文”“自动读取所有上游结果”来掩盖当前缺口。

### 面试时要守住的边界

- 当前是应用服务实现的 Leader-first 编排，没有使用 LangGraph 图执行器，也没有通用 DAG 调度器。
- 部分成功、失败、取消或等待输入可以触发协调检查，不意味着平台自动选择了重试、换成员或补偿方案。
- 飞书发送受理和关键结果消息，不逐条展示内部工具事件；Squad 成员的普通完成消息会被过滤，避免把成员完成误报为整体完成。
- 飞书消息主要依据 `IssueOrigin.conversation_id` 回到原会话，不保证完整恢复所有话题、消息树关系。

## 五、“开发过程中最难的部分是什么”：推荐讲输入合并与执行边界

### 选哪个故事，为什么

优先讲：**用户不断补充要求时，怎样既减少重复启动，又让正在执行的 Agent 和后续任务各自拿到正确输入。**

这个故事有一个容易理解的矛盾：用户希望新要求尽快生效，但 Agent 已经开始的一轮不能被事后改写；平台希望少启动几次，又不能把有效要求去重掉。故事可以从一条业务消息自然推进到事务、并发竞争和输入快照，既有业务动机，也有代码与测试支撑。

不建议第一句就说“最难的是 PostgreSQL UPSERT”，那只是解法之一。难点应放在**明确哪一轮负责哪一批要求，并让并发执行遵守这个约定**。也不优先拿“共享记忆”或“租约可靠性”作为已经攻克的主故事：当前这两部分仍有明确缺口。

如果面试官更关注多 Agent，可以在这个故事讲完后接 Squad 的汇总时机，作为同一个问题在多人协作下的延伸，不必开场同时讲两套复杂流程。

### 可直接练习的回答：约两分钟

下面是依据实现组织的方案讲述。只有确实由你负责的部分才能用“我”；“考虑过某种方案”也应符合真实经历。代码可以证明当前机制，不能证明你当时按这个顺序开发，更不能证明发生过线上事故。

> 我觉得最难的是处理用户连续补充要求和 Agent 执行之间的时间关系。
>
> 比如用户先说“帮我排查订单同步失败”，接着发日志，再补一句“重点看重试逻辑”。这三条消息可能在 Agent 启动前到，也可能在它已经开始分析后到。每条消息都启动一轮会重复分析；但直接修改正在执行任务的输入，又说不清它这一轮到底看到了什么。
>
> 我把问题拆成两个约束：同一事项、同一 Agent 最多保留一个待执行任务；任务一旦被领取，这一轮要消费的评论集合就固定下来。领取前的补充合并到当前待执行任务，领取后的补充进入下一轮，并等待前一轮结束。
>
> 实现上，待执行任务的唯一性用 PostgreSQL 部分唯一索引约束，评论通过 UPSERT 合并，避免并发请求都查到“没有任务”后各建一条。但仅做到这里还不够，因为 Agent 领取任务和新消息到达也会竞争。所以领取时，我把评论 ID 固化到任务里，生成 Prompt 只读取这一批评论，而不是直接读取事项下的全部评论。
>
> 验证时，我分别检查了领取前连续补充、领取后多条补充，以及领取后追加评论不会混入本轮 Prompt。这样就能用具体记录说明这一轮处理了哪些输入、哪些留给下一轮。当前没有线上调用节省的统计，我能确认的是这些场景下的合并和执行边界。
>
> 这部分让我意识到，多 Agent 平台需要把用户的连续输入划成明确的执行批次。输入归属不清楚，后面的会话恢复和结果追踪也很难解释。

**第一轮最适合停在第四段末尾**，让面试官追问“领取与合并并发时怎么办”。如果对方让你完整讲完，再继续测试和收获。不要为了讲满两分钟提前用完所有技术细节。

### 故事的三个转折：如何讲出思考过程

这些是方案取舍，不是仓库已证明的历史版本。未实际实施的方案用“如果这样做，会……”来讲。

| 转折 | 可以怎么说 | 展示的判断 |
|---|---|---|
| 从“一条消息一次调用”到“保留输入、合并执行” | “用户的几条补充可能共同描述一个要求，所以不能把消息数量直接当作执行次数。” | 先理解业务对象，区分 Issue、Comment 和 Task。 |
| 从“应用层查一下”到“数据库维护唯一性” | “两个请求都可能查到没有待执行任务，所以这个约束需要在数据库写入时成立。” | 把并发不变量落到存储层，而不是依赖请求时序。 |
| 从“能合并”到“明确哪轮消费” | “即使只有一个待执行任务，如果 Prompt 随时读全部评论，本轮输入还是不确定，所以领取要成为边界。” | 不只减少任务条数，也保证执行输入可解释。 |

第三个转折最有辨识度。面试官可能见过很多“唯一索引防重复”的项目，而“为什么任务不重复仍然不够”能体现你对 Agent 执行过程的理解。

### 面试官继续追问时怎么接

**“你真正解决的技术难点是什么，不就是一个唯一索引吗？”**

> 唯一索引只解决待执行任务数量的问题。还要处理本轮输入在哪里截止、后续任务什么时候能启动，以及原始消息能否追溯。我把它们分别落在部分唯一索引、领取时保存消费集合、领取 SQL 排除同一 Issue/Agent 活跃任务，以及独立保存 Comment 上。每个机制解决一个约束，缺一个都不能完整满足业务要求。

**“消息到达和任务领取正好同时发生，怎么办？”**

> 合并与领取都要更新数据库里的任务行。新消息先合并成功，领取就会看到它并放入本轮集合；领取先成功，原任务已经退出 queued，新评论应进入后续待执行任务。关键是由数据库写入竞争确定归属，而不是用应用层读取到的旧状态决定。这里保证的是数据库可见的处理边界，不是跨渠道按用户发送时间建立全局顺序；真实并发交错还需要专门的数据库并发测试，现有顺序测试不能代替它。

**“为什么不直接防抖两秒？”**

> 防抖可以帮助收集短时间内的消息，但 Agent 可能执行几分钟，用户也可能一直补充。固定窗口不能单独决定执行中的要求怎么办。我现在采用领取边界；如果以后做即时 Chat，可以在前面增加短静默窗口，但仍需要持久化和后续任务的规则。

**“执行过程中用户说不要改代码了，你这个方案还能保证吗？”**

> 不能。普通补充排下一轮，不会追溯改变正在执行的动作。紧急停止应走已有的取消请求，而不是把一条普通评论当成撤销。即使取消成功，已经发生的文件修改或远程调用也不会自动回滚。这是排队补充与中断控制需要分开的业务语义。

**“你怎么证明不是写了几个理想路径测试？”**

> 我会具体展示边界测试：先领取，再追加新评论，最后断言本轮 Prompt 只有领取前的评论；另一个测试是在已有执行时连续补充两条，检查只生成一个待执行后续任务。数据库集成测试还检查实际 UPSERT 合并和领取集合。但当前没有据此证明所有并发、租约过期和数据库故障组合都正确，这些需要继续补专门的验证。

对应 [评论合并测试](../../tests/test_comment_routing_and_merge.py) 中的 `test_running_task_gets_at_most_one_queued_successor`、`test_prompt_uses_only_the_claimed_input_snapshot_in_order`，以及 [数据库集成测试](../../tests/test_postgres_channels_integration.py) 中的 `test_postgres_merges_queued_comments_and_snapshots_them_when_claimed`。

### 如果面试官偏多 Agent：补一个 30 秒延伸

> 这个输入和执行时机的问题放到 Squad 里还会更复杂：成员没做完时，Leader 不应该提前汇总；几个成员先后完成，也不能各自启动一轮汇总。我用委派来源标识同一批成员，在 Issue 行锁内检查这一批是否仍有活跃任务，以及是否已有待处理的 Leader，再决定是否唤醒。还有一个容易遗漏的状态是成员等待输入：它已经交回控制权，如果一直等它成功，小队就会卡住，所以也要允许 Leader 接手协调。

这段可引到“模型决定分工、平台控制推进时机”。不要顺势声称已经解决完整共享上下文：当前 Worker 输入和 Leader 摘要仍有前文所述限制。

### 这道题不要这样答

- 不把“接了很多协议、代码量很大”作为难点结论，要讲哪两个要求互相牵制、你如何取舍。
- 不编造“上线后重复执行导致事故，排查三天”的经历。可以说“我用这个场景解释设计”“测试覆盖了这个边界”。
- 不承诺调用减少某个百分比、严格一次执行、绝不丢消息；当前证据支持的是具体机制和测试场景。
- 不把“继续补充”描述成“实时干预本轮 Agent”。这个区别本身就是能体现产品判断的追问点。

## 六、第二个难点故事：跨 Agent 交接时，如何让接手者拿到正确上下文

### 这个故事适合什么时候讲

如果面试官关注 Agent 架构、上下文工程或多 Agent 协作，优先展开这一题；偏后端并发和可靠性时，先讲上一节的输入合并。两者可以用一句话串起来：**前一个难点是同一 Agent 的哪一轮处理哪些消息，后一个难点是换了 Agent 后，它凭什么理解此前的工作。**

当前最准确的定位是”已经识别并分析的架构难点，跨 Agent 的按需读取链路已在本地 CLI Agent 落地（`mica-ctx`，含端到端测试），参考 Multica 明确了后续改进方案”。文件级交接和显式依赖装配尚未落地，所以如果面试官要求讲一个已经解决、可以验收的开发难题，仍以第五节为主。

### 用一个具体场景开头：路由成功，交接却可能失败

用户让 Agent A 分析订单同步异常，A 在评论中发布方案；用户接着说：

> `@agent:b 请审核 A 的方案，重点看幂等设计。`

平台能正确创建 B 的 Task，但当前 B 的 Prompt 主要包含 Issue 标题、正文和这条触发评论。A 的方案即使已经保存为评论，也不会自动进入 B 的输入。如果 B 以前参与过这个 Issue，恢复的也只是 B 自己的 Session。

于是出现一个很有故事性的反差：**系统确实把工作派给了正确的人，但没有把被审核的材料一起交过去。** 这不是一次已经验证发生的模型错误案例，而是从当前输入构造可以确定存在的信息缺口。

把同一问题放到 Squad：Geometry 返回一份较长的约束 JSON，Leader 摘要只保留其中一部分，然后交给 Placement。即使每个成员都正常返回，关键约束也可能在交接中被遗漏。任务状态成功不能证明协作信息完整。

### 可直接练习的回答：约两分钟

> 另一个我认为很关键的难点，是不同 Agent 之间怎么交接上下文。比如 A 已经分析出一个方案，用户让 B 审核，平台能把任务路由给 B，但 B 不一定拿到了 A 的方案。它们可能是不同模型、不同协议，恢复 B 自己的 Session 也不会自动得到 A 的历史。
>
> 我沿着代码检查了从评论路由到 Prompt 构造的链路：当前能传入本轮评论，也能复用同一 Agent 的会话；但跨 Agent 主要依赖 Leader 的委派说明和结果摘要。这样在短任务里能打通流程，遇到后续约束或长 JSON 就容易缺信息。问题在于平台没有明确这次任务依赖哪份上游结果。
>
> 我参考了 Multica 的源码。它让 Agent 保留各自的 Session，通过工具读取同一份 Issue 和评论线程；本轮触发评论直接放进输入，其他讨论先看线程摘要，再按需展开。Leader 的委派主要说这次找谁、做什么、有哪些额外约束，不用负责复述全部背景。
>
> 基于这个思路，我把后续方案分成三部分：Issue 保存共享事实，Session 保存某个 Agent 自己的连续历史，Task 明确本轮要处理的评论和依赖的结果。像“审核 A 的方案”，应该关联到 A 发布的具体结果；长 JSON 则保留完整产物和版本，不能只让 Leader 转述一段摘要。
>
> 当前 Mica 已实现同一 Agent 的续接和本轮评论消费集合；跨 Agent 这一侧，本地 CLI Agent 已经可以通过 `mica-ctx` 按需读取同一份 Issue 评论——B 能自己拉到 A 发布的结果评论这条最小链路已经打通，并有端到端测试覆盖。还没有落地的是显式的结果引用、版本边界和 ACP/A2A 侧的通道。下一步先处理文件与结构化结果的引用装配，再处理增量提示。这部分最重要的取舍，是既让成员拿到充分信息，又避免把全部历史重复塞给每一个 Agent。

这段明确区分“当前实现”“参考源码”“计划改进”。不要把最后两段改成“我们已经实现了”，也不要把 Multica 的功能算作个人开发成果。

**建议埋点：**“恢复了 Session，不代表拿到了其他 Agent 的结果；有读取工具，也不代表本次任务已经拿到了正确版本的输入。”讲到这里可以停下。

### 三个转折，让故事有推进而不只是介绍概念

| 转折 | 表面上看似可行 | 为什么还不够 | 应形成的设计判断 |
|---|---|---|---|
| 从路由到信息交接 | 正确 @ 到 B 就算交接完成 | B 不知道“A 的方案”具体是哪条评论、哪一版结果 | 确定执行者后，还要确定任务依赖的对象。 |
| 从会话恢复到共享事实 | 复用 Session 就有上下文 | Session 属于具体 Agent，可能过期或不可恢复 | 公共结论持久化，私有会话分别续接。 |
| 从 Leader 复述到按需读取 | Leader 总结所有结果给成员 | 长 JSON 会截断，重要约束可能遗漏；全量复制又增加成本 | 必需输入直接给，扩展背景可查询，长产物传稳定引用。 |

### Multica 真正可以借鉴什么

本节核对的是本机 Multica 源码，HEAD 为 `ca47495fcc3c4d2d0d6c7a421e45ddd0de98f0fd`，不声称代表其他版本。

| 已核对的实现 | 对 Mica 的启发 |
|---|---|
| `buildPromptBody()` 提供 Issue ID，引导 `issue get`、评论线程摘要和相关线程展开 | 把共享上下文做成可读取的资料，而不是只靠一段 handoff。 |
| `buildCommentPrompt()` 直接注入触发评论、合并评论及其来源信息 | 必须处理的本轮输入不能完全依赖模型自行检索。 |
| Squad briefing 要求成员自行读取 Issue 背景，Leader 简短说明职责和额外约束 | Leader 负责协调，公共背景不靠 Leader 反复转述。 |
| 评论 Prompt 区分正常恢复、增量已知、增量未知和重建 | “没有变化”与“没查到变化”不同；退回旧 Session 不能当成完整恢复。 |
| `GetLastTaskSession` 按 Agent/Issue 查询，并过滤不可恢复的历史会话 | 恢复前要判断会话是否可用；这里也不应被描述为已经按 Squad 角色隔离。 |

源码入口：`server/internal/daemon/prompt.go`（Prompt 构造）、`server/internal/handler/squad_briefing.go`（Squad 协作指令）、`server/pkg/db/queries/agent.sql`（Session 查询）。工具读取指令属于 Agent 执行约定，不能据此承诺模型必然读取了全部必需资料。

### 面试官追问时怎么答

**“为什么不把 A 的对话记录直接给 B？”**

> A 的历史里混有角色指令、工具过程、旧方案和被推翻的判断，完整复制会增加噪声与成本，不同 Provider 的 Session 也不是可直接互换的格式。B 应拿到审核对象、必要依据和用户约束；需要深入追溯时，再读取相关公开记录。并不是任何内容都不能共享，而是要以明确的业务资料交接。

**“为什么不每次把 Issue 全部评论都放进 Prompt？”**

> 短任务可以这样做，但长事项会重复输入大量无关历史，多个版本的结论也容易混淆。我更倾向于直接装配当前要求和明确依赖，再提供线程摘要及按需读取入口。不能为了省 Token 连本轮必须审核的方案都只给一个模糊提示；没有实测数据时，也不能承诺按需读取一定节省多少。

**“@B 审核 A 的方案，你准备怎么落地？”**

> 先支持明确选择 A 的结果评论，沿已有的 `source_task_id` 找到产出任务，将这个依赖记录在 B 的任务输入里；普通模糊 @ 文本不强行猜成某个最新结果。平台校验对象归属和访问范围后，为 B 装配完整审核对象及相关要求。第一步可以复用已有 Comment 和 Task.output，不必先建完通用记忆系统；长文件、JSON 和多版本结果再引入 Artifact。目前 B（CLI 侧）已能通过 `mica-ctx` 主动读到 A 的结果评论，但"任务显式声明依赖对象、平台负责装配"这层逻辑尚未实现。

**“结果已经在数据库里了，还缺什么？”**

> 缺的是从数据到本次执行输入的确定链路。当前虽然保存了 Agent 结果评论和 Task.output，B 的 Prompt 也不会因此自动包含它们；CLI Agent 现在可以用 `mica-ctx` 自己读到，但"任务明确引用了哪个对象、能否查到这轮实际使用的版本"仍然没有记录。存得下来、读得到、这轮确实读了，是三个不同要求——前两者已具备，第三个仍缺读取回执。

**“Agent 没有本地 CLI，怎么读取共享上下文？”**

> Multica 的本地 CLI 读取方式不能原样要求远程 A2A Agent 使用。Mica 可以由平台先解析依赖并把必要内容放进 A2A Message；若远端支持工具接入，再提供有权限范围的读取接口。共享的是数据与引用约定，传递方式由 Provider 能力决定。目前统一装配与授权读取层还没有落地。

**“按需读取会不会读到用户刚修改的新版本？”**

> 会，如果只有动态查询就没有固定输入边界。因此拟议的任务输入清单还要绑定评论、结果或产物的具体版本；查询按这个边界返回，后续变更留给下一轮或显式追加记录。仅保存 ID，而对象内容可以覆盖修改，并不足以保证可重现。当前 `delivered_comment_ids` 也不能被说成完整上下文版本快照。

**“同一个 Agent 已经处理过，为什么还要读公共上下文？”**

> 它自己的历史不知道其他 Agent 后来发布了什么，也不知道用户新增了什么。会话连续时可以读取上次之后的变化；会话丢失、退回旧会话或增量未知时，需要重建必要背景。参考 Multica 的关键是判断连续性，而不是每轮重复全量读取，也不是有 Session ID 就完全不读。

**“怎么判断这个改进真的有效？”**

> 我会设计明确的验收场景：A 发布两版方案，B 指定审核第一版时不能误读第二版；用户在 A 完成后补充限制，B 必须拿到本轮要求；长 JSON 经过交接仍然完整；B 没有历史 Session 时仍能完成同样的读取；跨 Issue 或未授权引用必须拒绝。这些是拟新增的验收测试，不是目前已经通过的测试。

### 推荐的讲述顺序

先用“B 审核 A 却没拿到方案”把业务问题说清，再解释共享事实、私有会话和本轮输入三个层次；最后讲 Multica 的参考及 Mica 的落地边界。版本、增量、权限和 Artifact 留给追问，不要开场同时抛出四层架构、五个字段和多个协议名。

与上一节一起准备时，可以这样回答“最难的是什么”：**“执行层面，我重点处理了连续输入与任务领取的边界；协作层面，更值得深入的是跨 Agent 信息交接，目前打通了基础续接，也明确了共享上下文的下一步方案。”** 然后按面试官兴趣选一条展开。

## 最后练习：把回答控制在面试官当前问的层次

每一点都按“用户遇到什么问题 → 平台做了什么 → 为什么有一个关键设计”讲第一轮。先记住下面四句，不必背全部实现细节：

| 简历点 | 第一轮留下的核心句 |
|---|---|
| 消息合并 | “并发到达时守住一个待执行任务，领取时固定本轮输入。” |
| 本地执行 | “代码状态与对话状态都要续接，并且先拿容量再领任务。” |
| 异构接入 | “统一的是执行语义，等待输入与结构不合规不能被当成成功。” |
| Squad | “模型决定分工，平台校验委派并控制汇总时机，用户最终验收。” |

遇到“你怎么验证”的追问，回答具体行为测试，例如“领取后再追加一条评论，断言它没有进入本轮 Prompt”，比只说“写了单测”更有说服力。上一次本地检查为 264 通过、4 跳过；跳过项需要一次性 PostgreSQL 测试库，不能把这组结果说成全量数据库集成验证或真实模型验收。

遇到“效果提升多少”的追问，没有统计就讲机制和可验证例子，不编造调用减少比例、并发规模或生产事故。对已知缺口，可以结合 [已知问题](../known-issues.md) 说明当前行为、影响和下一步改法。
